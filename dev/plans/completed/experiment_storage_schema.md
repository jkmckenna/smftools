# Design: formal parquet/zarr experiment storage schema

**Status:** complete — all four phases implemented. Verified against the code
2026-08-26, not taken from this document's own claims: `write_raw_store` emits
`molecules.parquet` and `barcode_index`, `experiment_manifest.py`,
`stage_obs.py` and `experiment_spine.py` all exist and are wired, and spatial
writes `group_path`/`obsm_keys` with `partition_read.py` keeping a
`read_metrics_path` fallback for catalogs written before the rename — a
migration path, not an unfinished phase.

Phases 1-2 implemented: `molecules.parquet`/`Sample`-in-sort-key/
`barcode_index.parquet` (`informatics/raw_store.py::write_raw_store`), and
`experiment_manifest.json` (`informatics/experiment_manifest.py`, wired into raw only).
Phase 3 implemented: normalized per-stage `obs.parquet` exists for raw and preprocess
(via `informatics/stage_obs.py`), and a consolidated `experiment_spine.h5ad` is
generated by `informatics/experiment_spine.py` -- **as an additive superset cache
alongside every stage's own `spine.h5ad`, not a replacement for it** (a materially
different, lower-risk design than originally sketched below -- see "Consolidated
experiment_spine.h5ad: revised design" for why). Phase 4 implemented, also narrower
than originally sketched: `X` co-location in preprocess's own task shards (with a
single-shard-coverage fast path in `materialize()`) and spatial's `read_metrics.zarr`
catalog normalization (`group_path`/`obsm_keys`, replacing the bespoke
`read_metrics_path` column) -- the `store_catalog.parquet` filename rename was
explicitly scoped out. See "Suggested phasing" for what each covers.

## Motivation

The current per-experiment storage (raw ragged parquet + task-based zarr shards +
`spine.h5ad` + assorted catalog parquets) already gets several things right by
construction, confirmed by reading the actual code, not assumed:

- **Ragged (variable-length) per-read arrays are already parquet** (`ragged_store.py`).
- **Dense uniform per-task matrices are already zarr** (task shards addressed by
  `preprocess_catalog`/`hmm_catalog`).
- **Partitioning is already reference-based, not sample-based** -- raw partitions by
  `(Reference_strand, start_bin)`, preprocess/hmm tasks partition by
  `(reference, genomic core window)`. Sample/barcode is an obs column today, never a
  partition boundary. (`partition_store.py`'s `(Reference_strand, Sample)` partitioning
  is dead code, kept only for test fixtures -- see that module's own docstring.)
- **Expensive data is never copied forward.** A stage's derived layers live only in
  that stage's own task catalog; `materialize()` stitches them onto a selection at read
  time. `spine.h5ad` obs *is* copied forward stage to stage (`.copy()`), but that's
  cheap scalar columns, not arrays.

Four concrete gaps, identified from this same review:

1. **No formal molecule-ID catalog.** Canonical read ordering is implicit --
   whatever order `raw_store.py`'s `sort_values([Reference_strand, start_bin,
   reference_start, read_id])` produced, inherited by every derived spine via
   `.copy()`. There's no standalone artifact that *is* the ordering.
2. **Rows aren't barcode-sorted.** Within a `(reference, window)` partition, rows are
   sorted by `(start_bin, reference_start, read_id)` -- not by sample. A per-barcode
   query today is a scan + boolean mask, even though zarr's own chunking could support
   a contiguous slice if rows were ordered for it. (This is the exact optimization the
   user's own lab convention already documents as the *target* for the project-level
   read cache -- "Zarr with obs sorted by barcode: 138ms per barcode vs 1s for backed
   h5ad" -- just not yet pushed down to the experiment level, which is the right place
   to do it once instead of re-sorting in every downstream cache.)
3. **Config params and input data path aren't captured in the store at all** -- only a
   `config_hash` (staleness check, not the values) lives in the task catalog.
   `input_data_path` lives solely in the external `experiment_config.csv`, which
   doesn't necessarily travel with the store.
4. **No `obsm` analog, and derived per-read outputs already fragment into a second
   zarr file per task.** Spatial's per-task read-level outputs
   (`tools/partitioned_spatial.py`) are *already* built as
   `ad.AnnData(obs=read_obs, obsm=read_obsm, uns=read_uns)` -- an obsm-shaped object --
   but written to a standalone `read_metrics.zarr`, sibling to that same task's
   layers-only `ad.AnnData(obs=obs, var=var, layers={...})` (no `X`, no `obsm`) in
   `shard.zarr`. Two zarr files per task, addressed by two different catalog columns
   (`group_path` and `read_metrics_path`), for data that's computed together and
   belongs together. The project-level embedding work (`embedding_store.py`) has the
   same shape problem one level up: bare `pca_space.npy`/`coords.npy`/`clusters.npy`
   files with a hand-rolled `meta.json`, because there's nowhere formal to put a
   per-molecule derived matrix.

## Goals

- One documented, named schema with explicit AnnData analogs (`obs`, `var`, `X`/
  `layers`, `uns`, `obsm`), so the on-disk format is easy to explain and predict.
- Formalize the molecule-ID catalog and barcode-sorted row order as first-class,
  documented artifacts -- both already-identified, concrete wins.
- Close the config/input-path provenance gap with one consolidated manifest.
- Define the missing `obsm` analog by co-locating it with `X`/`layers` inside the same
  per-`(reference, window)` zarr store that already computes it, rather than a separate
  sidecar file or a new top-level stage.
- Stay evolutionary: every existing production code path (registry, `materialize()`,
  the project-layer stores built this session) keeps working. `spine.h5ad` is
  demoted to a **generated cache** -- one per experiment, not removed, not per-stage.

## Non-goals

- Not a rewrite of the ragged-store or task-catalog mechanisms -- those already match
  the target shape (parquet for ragged, zarr for dense, catalog-stitched at read time).
- Not eliminating AnnData from the read path. It stays the in-memory analysis object;
  only the on-disk source of truth changes shape.
- Not solving per-sample partition-native set-store integration here -- that's
  `project_sample_and_set_stores.md`'s open item (per-sample, not per-experiment,
  granularity).

## Schema: AnnData analogs

| AnnData concept | On-disk analog | Status |
|---|---|---|
| Molecule identity/order | `molecules.parquet` (top-level, one per experiment) | **new** |
| `obs` | `<stage>/obs.parquet` -- stage-specific new columns only, joins to `molecules.parquet` + earlier stages' `obs.parquet` by `read_id` | **new** (replaces `spine.h5ad` obs as source of truth) |
| `var` | `<stage>/var.parquet` | already exists (`preprocess_var`) -- formalized as the pattern for every stage |
| `X` / `layers` / `obsm` | `<stage>/stores/.../store.zarr` (one zarr store per `(reference, window)` task -- `X`, `layers`, `obsm` co-located) + `<stage>/store_catalog.parquet` | `layers`/catalog already exist (`preprocess_catalog`/`hmm_catalog`); `X` co-location and `obsm` co-location are **new** -- see "Store organization" below |
| `uns` | `experiment_manifest.json` (top-level) | **new**, consolidates config params, input path, FASTA path, stage/config-hash index, sidecar registrations -- see below |
| `varm`/`obsp`/`varp` | not used | out of scope; no current producer |

`spine.h5ad` is demoted to **one generated, denormalized convenience cache per
experiment** (`experiment_spine.h5ad`, top-level, alongside `molecules.parquet`) --
not one per stage. It's the join of `molecules.parquet` + every stage's `obs.parquet`
that has run so far, regenerated as stages complete, so `is_spine`/pointer-based code
and ad hoc `sc.read_h5ad(...)` exploration keep working unchanged against one always-
current file. See "One experiment-level spine, not one per stage" below for why a
single cache is sufficient and what stays genuinely per-stage regardless.

## Store organization: parquet stores vs. zarr stores

Two kinds of artifact, and every file in this schema is one or the other:

**Parquet stores** -- tabular/catalog data, queryable with predicate pushdown, no
big dense arrays: `molecules.parquet`, `<stage>/obs.parquet`, `<stage>/var.parquet`,
`<stage>/store_catalog.parquet`, `barcode_index.parquet`. (`experiment_manifest.json`
is metadata, not tabular -- JSON, not a parquet store.)

**Zarr stores** -- one per `(reference, window)` task, each a directly-openable
`anndata.read_zarr()` object (`X`, `layers`, `obsm`, plus minimal `obs`/`var`/`uns` for
standalone readability -- the *authoritative* obs/var/uns are the parquet stores and
manifest above; a zarr store's own copies are just enough to make it self-describing
when opened directly). This is the actual mechanism change from today: `safe_write_zarr`
is already AnnData-based (confirmed in `partitioned_executor.py`/`partitioned_spatial.py`
-- both already construct an `ad.AnnData(...)` before writing), so this isn't a new I/O
path, just changing which AnnData slots get populated before the existing writer runs:

- **`X`**: the dense per-position signal matrix, written **once**, by whichever stage
  first materializes it densely for that `(reference, window)` -- in practice
  `preprocess` (today's `_core_result` builds `layers` only, no `X`; this adds it).
  Later stages (`spatial`, `hmm`, ...) do **not** duplicate it into their own store --
  duplicating a dense signal matrix into every stage's zarr store would reintroduce
  exactly the copy-forward cost the layer catalog already avoids for derived layers.
- **`layers`**: each stage's own newly-computed derived layers only (unchanged from
  today) -- `binarized_methylation`/`nan_half` from preprocess, HMM state calls from
  hmm, etc. Stitched onto the owning stage's `X` at `materialize()` time via the store
  catalog, exactly like today's `_overlay_preprocess_layers`.
- **`obsm`**: per-read, non-position-indexed outputs computed *for the reads in that
  task's interval* -- autocorrelation curves, Lomb-Scargle periodograms. This is
  spatial's `read_metrics.zarr` folded into the same store as that task's `layers`,
  not a separate file: `read_obsm` (already built as its own `ad.AnnData` today, per
  the motivation section) becomes the `obsm=` argument of the *same* `ad.AnnData(...)`
  call that builds `layers`, one zarr write instead of two.

A later stage's `materialize()` call resolves `X` by walking back to the owning
stage's store (same `(reference, window)` key, already how cross-stage pointers like
`source_base_dir` work today), then overlays its own and every intermediate stage's
`layers`/`obsm` on top -- the read path doesn't change in kind, only in exactly which
store `X` comes from.

## On-disk artifacts, in detail

### `molecules.parquet` (new, top-level, written once by raw)

One row per molecule that ever existed in the experiment (raw's full read set --
later stages are subsets of this, never supersets). Columns: `read_id`,
`Reference_strand`, `Sample`, `canonical_row` (the ordering every zarr partition's row
index derives from). Immutable after raw writes it. Every later stage's `obs.parquet`
and every task's zarr shard address molecules by `read_id`, never re-establishing their
own ordering.

### `experiment_manifest.json` (new, top-level, consolidates today's scattered `uns`)

Replaces the informal mix of `spine.uns` keys and `sidecar_manifest.json` with one
readable index, appended to (not replaced) by each stage as it runs:

```json
{
  "experiment": "<run-id>",
  "modality": "deaminase",
  "input_data_path": "../../../data/<run-id>",
  "fasta_path": "./BALBC_B6_NKG2A_ZC_array_mNanog.fasta",
  "reference_uids": {"6B6_top": "157528f28fb50d19", "...": "..."},
  "reference_lengths": {"6B6_top": 4690, "...": "..."},
  "config": { "...resolved experiment_config.csv fields, by value..." },
  "stages": {
    "raw": {"config_hash": "...", "completed_at": "...", "n_molecules": 188870},
    "preprocess": {"config_hash": "...", "completed_at": "...", "n_molecules": 8008}
  }
}
```

This directly closes gaps 3 and (partially) the "which stages have run" question --
`stages` is a readable index in one place, in addition to (not instead of) the existing
structural signal (does `<stage>_outputs/` exist).

### `<stage>/obs.parquet` (new shape; replaces spine-obs-as-source-of-truth)

Only the columns that stage *produced* -- e.g. preprocess's holds `passes_read_qc`,
`is_duplicate`, dedup-cluster id; hmm's holds nothing extra if it only adds layers.
Never re-stores `Reference_strand`/`Sample`/`bam_path`/etc. -- those live once, in raw's
`obs.parquet`. A full obs view for a stage is `molecules.parquet ⋈ raw/obs.parquet ⋈
... ⋈ <stage>/obs.parquet` by `read_id`.

### `<stage>/var.parquet` (already exists as `preprocess_var`; formalized as the pattern)

Position-level annotations (coverage, valid-fraction, per-reference peak/consensus
columns). Already correctly *not* copied forward or unioned across experiments --
`project.catalog.project_adata` already strips it when pooling (see the var-column-
overflow fix from real-project testing).

### `<stage>/store_catalog.parquet` + `<stage>/stores/.../store.zarr` (renamed/reshaped from today's task catalog + shard)

Renamed from `preprocess_catalog`/`hmm_catalog` + `_task_path`-addressed shards to
match the "parquet store / zarr store" vocabulary; same row shape (`reference`,
`core_start`, `core_end`, `group_path`, `layers`), plus an `has_x` bool and an
`obsm_keys` list column so a reader knows without opening the zarr store whether it
owns `X` and which `obsm` keys it carries. Two changes from today: **row order within
each store is barcode-sorted** (see below, with a per-partition `{sample: (start_row,
end_row)}` index for contiguous per-barcode reads), and **the zarr store itself now
carries `X`/`layers`/`obsm` together** per "Store organization" above, replacing the
separate `read_metrics.zarr` + `read_metrics_path` catalog column spatial uses today.
`"task"` stays the internal compute/scheduling term (`PreprocessTask`,
`execute_preprocess_task`, ...) -- only the on-disk artifact names change.

### Barcode-sorted row order (the concrete, low-risk win)

Today: raw sorts by `(Reference_strand, start_bin, reference_start, read_id)`. Proposed:
sort by `(Reference_strand, start_bin_or_window, Sample, read_id)` instead -- reads from
one barcode become contiguous within their reference/window partition. Paired with a
per-partition `barcode_index.parquet` (`sample, start_row, end_row`), a "give me one
barcode's reads for this reference" query becomes a direct row-slice instead of a
scan + boolean mask. This is the exact technique already validated at the project-cache
level; this pushes it to the source so every downstream cache inherits it for free.

### Consolidated `experiment_spine.h5ad`: revised design (implemented)

The original plan below (single spine, replaces every per-stage `spine.h5ad`,
`registry.py`'s `spines: {stage: path}` repurposed to mean "which stage's
`store_catalog.parquet`") was **not what got built**, after mapping every call site
that depends on today's semantics (`project/registry.py`, `catalog.py`,
`set_store.py`, `sample_store.py`, `sample_analysis.py`, `cli/project_cmd.py`,
`cli_entry.py`, `materialize()` itself and its `_overlay_*` helpers -- roughly 15
call sites). Most of them rely on resolving one *specific* stage and getting back a
**self-contained** spine (its own obs *and* its own `uns` catalog pointers) -- e.g.
explicit `--stage preprocess` pinning, `sample_store.py` reading `Reference_strand`/
`Sample` off one resolved spine. Replacing per-stage `spine.h5ad` outright would have
broken all of that for no real gain, since `STAGE_PRIORITY` fallback already picks
the single most-derived stage automatically today.

The actual unmet need: **spatial and hmm are sibling branches off preprocess, not
sequential to each other.** Whichever one's `spine.h5ad` a caller resolves to only
carries that one lineage's `uns` catalog pointers forward via `.copy()` -- there was
no way to get spatial's read-metrics *and* hmm's derived layers in one
`materialize()` call, because no single spine's `uns` ever had both at once.

There's also a structural reason the literal top-level placement below doesn't work:
`materialize()`'s `_resolve_spine`/`_run_root_from_spine_path` hardcode "a spine
lives two directory-levels under the run root" (`<run>/<stage>_outputs/spine.h5ad`)
to resolve `uns['source_base_dir']`. A true top-level `<run>/experiment_spine.h5ad`
(one level, not two) resolves that anchor one directory too high.

**What's actually implemented** (`informatics/experiment_spine.py`): every stage's
own `spine.h5ad` is untouched, exactly as before -- zero behavior change for any
explicit `stage=` request, zero changes to the ~15 call sites found. A new,
generated file coexists alongside them at `<run>/experiment_spine_outputs/
spine.h5ad` (a stage-shaped sibling directory, not top-level, for the structural
reason above) -- `write_experiment_spine(run_root)`:

- builds `obs` from `informatics.stage_obs`: raw's `obs.parquet` inner-joined with
  preprocess's `stage_obs.parquet` when present (spatial/hmm contribute no obs
  columns, confirmed in Phase 3's status above, so there's nothing further to join);
- builds `uns` as the **union** of every stage spine's `uns` found under the run
  root (raw, preprocess, spatial, hmm, in that order -- later stages win on shared
  keys, safe since shared keys already hold the same value across stages by
  construction), not one linear `.copy()` lineage -- this is what lets one
  `materialize()` call resolve derived data from sibling branches together;
  `uns["source_base_dir"]` is then explicitly re-anchored to this file's own
  directory rather than trusted from the union.

Called once at the end of each of the four stage executors (`write_raw_store`,
`execute_partitioned_preprocessing`, `execute_partitioned_spatial`,
`execute_partitioned_hmm`) -- cheap (obs only, no big arrays), regenerated fresh
each time. `registry.py`'s `STAGE_DIRS` gained one entry (`"experiment":
"experiment_spine_outputs"`, so the existing generic discovery loop finds it for
free) and `resolve_experiment_spine(entry, stage=None)` prefers it over the
`STAGE_PRIORITY` chain when present -- a strict superset, so always at least as
complete an answer; explicit `stage=` requests are completely unaffected. Runs that
predate this (or haven't been reprocessed) fall back to `STAGE_PRIORITY` exactly as
before -- no forced backfill.

Proven end-to-end by `tests/unit/informatics/test_experiment_spine.py::
test_experiment_spine_resolves_sibling_branch_layers_together`: preprocess ->
spatial and preprocess -> hmm run as sibling branches, then one `materialize()` call
against `experiment_spine_outputs/spine.h5ad` pulls an hmm derived layer *and* a
spatial read-metric together -- the concrete case no single pre-existing per-stage
spine could do.

Note what disappeared relative to the earlier draft: no per-stage `spine.h5ad` (one
experiment-level file instead), no separate `read_metrics.zarr` (folded into each
store's `obsm`), no `latent_adata_outputs/` reshape (`obsm` lives wherever it's
computed -- inside the reference/window store that produced it -- not in a separate
top-level stage; a project-level embedding over a *pooled, cross-experiment* set
remains `project/embedding_store.py`'s job, which is a genuinely different scope).

## Read path: what changes in `materialize()`

Conceptually little. Today's dispatch (dense-cache / tiled / ragged-fallback, then
`_overlay_preprocess_layers`/`_overlay_preprocess_var`/`_overlay_spatial_read_metrics`)
already *is* "resolve a molecule selection, stitch catalog-addressed derived data onto
it." Three changes:

- Obs resolution reads/updates the single `experiment_spine.h5ad` instead of a
  per-stage spine -- still a cache, still cheap, just one file that's always current
  through whichever stage is most-derived, rather than N frozen snapshots.
- `X` resolution walks back to the owning stage's store (same `(reference, window)`
  key) when the requested stage's own store doesn't carry `X` -- the same kind of
  cross-stage pointer-following `source_base_dir` already does today, just applied to
  signal instead of just catalogs.
- `_overlay_spatial_read_metrics` simplifies: `read_metrics=True` becomes "does this
  already-addressed store have an `obsm` group with the requested keys," not a second
  catalog lookup (`read_metrics_path`) into a second file.
- Row-slice reads can use `barcode_index.parquet` for a direct contiguous read when a
  query is scoped to one/few samples, falling back to today's scan+mask otherwise.

## Relationship to existing code

Additive, not a rewrite, if `experiment_spine.h5ad` stays a generated cache:

- `informatics/partition_read.py` (`materialize()`, `_resolve_spine`,
  `_overlay_preprocess_layers`, `_overlay_spatial_read_metrics`): unchanged read
  *contracts*; obs resolution points at one file instead of per-stage files, `X`
  resolution gains an owning-stage lookup, read-metrics overlay simplifies to a
  same-store `obsm` check.
- `informatics/raw_store.py`: gains `molecules.parquet` + `barcode_index.parquet`
  writing, and the sort key changes to include `Sample`.
- `preprocessing/partitioned_executor.py`: `_core_result` gains `X=` (only when this
  stage owns it) alongside its existing `layers=`; `obs.parquet` becomes
  stage-columns-only instead of a full `spine.copy()`.
- `tools/partitioned_spatial.py`: the standalone `read_metrics = ad.AnnData(obs=...,
  obsm=..., uns=...)` + separate `read_metrics.zarr` write is removed -- `obsm=`
  becomes an argument to the same `ad.AnnData(...)`/write call that already builds that
  task's `layers`.
- `experiment_spine.h5ad` regeneration: **implemented** as an explicit step at the
  end of each of the four stage executors (see "Consolidated experiment_spine.h5ad:
  revised design" above) -- not lazy, not a separate CLI command.
- `project/registry.py`: **implemented**, but more minimally than originally
  sketched -- `spines: {stage: path}` keeps its existing per-stage meaning
  unchanged for every stage; it gained one *additional* entry
  (`"experiment": "experiment_spine_outputs"`) that `resolve_experiment_spine`
  prefers over the `STAGE_PRIORITY` chain in fallback mode only. `X`/layer/`obsm`
  resolution was **not** repurposed to `store_catalog.parquet` (Phase 4, not done
  yet) -- it still goes through whichever stage's own `spine.h5ad` `materialize()`
  resolves to, exactly as today.
- `project/catalog.py`, `project/set_store.py`, `project/sample_store.py`: no changes
  needed beyond following `registry.py`'s updated path resolution -- they don't
  hand-parse spine paths themselves.
- Legacy monolithic AnnData handling (`_materialize_legacy`, the registry's legacy
  adapter): fully unaffected -- this schema only describes the modern partitioned-store
  side.

## Migration / compatibility

- Existing runs already on disk keep working as-is (old per-stage `spine.h5ad` files,
  no `molecules.parquet`, no `experiment_spine.h5ad`) -- `materialize()`'s obs-
  resolution falls back to reading whichever spine it finds directly when no
  `molecules.parquet`/`experiment_spine.h5ad` is present, the same backward-compatible-
  reader pattern already used for absolute-vs-relative path encoding.
- No forced backfill: a run only gets the new artifacts by being (re)processed with an
  updated pipeline version, same as any other schema-version bump
  (`raw_schema_version`).

## Open questions

- ~~Exact regeneration trigger for `experiment_spine.h5ad`~~ -- **resolved**: eager,
  on every stage run, wired into all four stage executors.
- Whether `barcode_index.parquet` should live per-partition (as sketched) or as one
  top-level index across all partitions for a stage -- per-partition is simpler to
  write incrementally; top-level is simpler to query without knowing partition
  boundaries in advance.
- Whether `X` ownership should be pinned to "whichever stage first materializes it
  densely" (as sketched, in practice always `preprocess`) or made explicit/configurable
  per experiment -- pinning it implicitly to "first" is simple but means a stage
  executor must always check whether an earlier store already owns `X` for that
  `(reference, window)` before deciding whether to write its own.
- `var.parquet`'s ~1200-column case (the real project's HMM per-reference
  peak/consensus columns) -- parquet handles wide schemas better than HDF5's attribute
  limit, but is 1200 columns itself a sign those should be long-format
  (`position, column_name, value`) rather than wide, for easier cross-experiment
  querying?

   **Naming collision found and worked around, not designed away:** preprocess
   already owned `obs.parquet` (`PREPROCESS_OBS_SIDECAR`) for an unrelated,
   pre-existing artifact -- a denormalized *full* `spine.obs.copy()` that's also
   internal working state, read back and rewritten several times mid-function

   partitioned_spatial.py::execute_partitioned_spatial` and `tools/partitioned_hmm.py::

   already anticipated ("hmm's holds nothing extra if it only adds layers"). Per-stage

4. **Done, narrower than originally sketched.** Investigated all three stages'
   actual write paths before implementing (not assumed from this doc's earlier
   sketch) and found two of the three original sub-goals didn't hold as written --
   see below for what changed and why. Went back to the user for an explicit scope
   decision given the reshaped picture; both surviving pieces were built.

   **X co-location (implemented).** `X` was **100% absent** from every preprocess/
   hmm task shard before this -- not "half-present" as the original sketch implied.
   `materialize()` got `X` exclusively from raw's ragged/tiled/dense-cache
   reconstruction, completely decoupled from the preprocess/hmm task catalogs
   (which only ever *overlay* derived layers on top of an already-populated `X`).
   `preprocessing/partitioned_executor.py::_core_result` now passes `X=np.asarray
   (core.X)` when building each task's result AnnData (one line -- `core.X` was
   already in the exact obs/var order needed), and the task catalog gains a
   `has_x: bool` column (always `True` going forward; a missing column is the
   backward-compat signal for catalogs written before this change).

   Read side: a new, deliberately narrow fast path,
   `informatics/partition_read.py::_load_preprocess_x_selection`, tried first in
   `materialize()`'s dispatch, before the existing dense-cache/tiled/ragged chain
   (which is untouched below it). It only activates when a **single** `has_x`
   preprocess task shard fully covers the entire requested selection (one
   reference, every requested read present, the position window inside the
   shard's `core_start`/`core_end`) -- mirroring `_load_tiled_cache_selection`'s
   existing "single candidate must fully cover, else `None`" shape. Stitching `X`
   across *multiple* shards (a whole-reference query spanning several barcode-
   partitioned tasks) was deliberately not attempted: unlike layers (stitched onto
   an already-established shape, gaps NaN-fillable), assembling `X` from scratch
   across shards means reconstructing the row/column shape itself with zero
   tolerance for silent gaps -- meaningfully more complex, and a separable future
   increment if ever needed. In practice this still covers the common case:
   preprocess tasks are barcode-partitioned by default, so any single-sample-
   scoped `materialize()` call -- e.g. the project layer's per-sample streaming --
   hits this path. A second, sharp-edged guard found while testing: the fast path
   must never activate when the caller's `layers` request is `None` ("give me
   everything, including raw-sourced layers like `read_span_mask`") or non-empty
   (specific raw-sourced layers requested) -- a preprocess shard can never satisfy
   either, and the first version of this code silently returned an incomplete
   result before that guard was added (caught by a real caller,
   `partitioned_plots.py::_read_span_quality_plots`, in the test suite).

   **Spatial `obsm` normalization (implemented, corrected scope).** The original
   sketch said obsm gets "folded into the same store as layers," and was read
   (incorrectly, caught and corrected mid-implementation) as needing spatial's
   `obsm` to share a store with some *other* stage's `X`/`layers`. It doesn't:
   `X`/`layers` share one dimensionality (reads × positions) within a store, but
   `obsm` only needs read-axis alignment, with its own free-form column count per
   key -- there was never a dimensional-compatibility requirement to satisfy.
   Spatial also has no `layers`-shaped zarr shard at all (its durable outputs are
   `metrics.parquet`/`autocorrelation.parquet`/`positions.parquet` plus the
   optional `read_metrics.zarr`) -- there's nothing to fold obsm *into* on another
   stage's store. What actually shipped: spatial's own task catalog
   (`tools/partitioned_spatial.py::execute_spatial_task`) now uses `group_path` +
   `obsm_keys` (a list, empty when nothing was computed) instead of the bespoke,
   nullable `read_metrics_path` column -- the same store-per-task addressing
   convention preprocess/hmm's catalogs already use. `read_metrics.zarr`'s
   *content* is unchanged, only its catalog addressing. `_overlay_spatial_read_
   metrics` reads `group_path` when present, falling back to `read_metrics_path`
   for catalogs written before this change -- no forced backfill.

   **Not done:** the `store_catalog.parquet` filename rename (`catalog.parquet`/
   `task_catalog.parquet` → one consistent name across all three stages) --
   explicitly scoped out as pure bookkeeping with real mechanical blast radius
   (every `PREPROCESS_PARTITION_CATALOG`/`HMM_TASK_CATALOG` reader, several tests)
   for no functional benefit on its own.

   Tests: `tests/unit/informatics/test_preprocess_x_fast_path.py` (has_x marker
   written, fast path matches raw reconstruction exactly for a covering single-
   shard selection with a spy confirming raw reconstruction never runs,
   `layers=None` correctly never uses the fast path and still returns raw-sourced
   layers, multi-barcode selections spanning two shards fall back correctly,
   missing `has_x` column falls back gracefully, a requested window wider than
   the one covering task's core falls back correctly); `tests/unit/
   test_partitioned_preprocess_executor.py` (spatial catalog's `group_path`/
   `obsm_keys` assertions, a dedicated backward-compat case rewriting a fresh
   catalog back to the legacy `read_metrics_path`-only shape and confirming
   `materialize(read_metrics=True)` still resolves it).
